# 03 ContextWeave 架构验证方案 V0.1

## 1. 文档目的

本文定义 ContextWeave 关键架构设计的验证范围、验证方法和通过条件。功能验收以 `01-devcollab-product-requirements-v0.1.md` 为准，系统结构及技术约束以 `02-devcollab-system-architecture-v0.3.md` 为准。

验证结论必须来自可复现的自动化测试、压测数据或故障实验，不以理论分析代替实际结果。

## 2. 验证原则

| 编号 | 原则 | 要求 |
|---|---|---|
| VP-01 | 权威数据优先 | 故障后以 PostgreSQL 中的业务状态和操作记录核对最终结果 |
| VP-02 | 端到端验证 | 关键链路应覆盖客户端入口、服务边界、存储及异步处理，不只验证单个方法 |
| VP-03 | 重复与恢复 | 对操作重试、事件重复、消费者重启及派生数据重建进行验证 |
| VP-04 | 资源有界 | 检查连接队列、线程池、缓存、批次和任务配额在压力下是否保持边界 |
| VP-05 | 结果可追溯 | 保存环境、数据规模、执行步骤、指标、日志、Trace 及结论 |

## 3. 核心验收矩阵

| 场景 | 验证方法 | 通过条件 |
|---|---|---|
| 重复 operationId | 对同一文档重复提交同一操作 | 文档只修改一次，并返回原结果或等价幂等结果 |
| 同 Block 并发修改 | 两个客户端基于相同版本同时更新 | 一个操作成功，另一个收到明确冲突；内容不被静默覆盖 |
| ACK 丢失 | 服务端提交成功后模拟客户端未收到 ACK | 客户端重试不产生重复修改 |
| 客户端乱序 | 交换或缺失 clientSequence | 系统识别乱序或缺失并返回明确处理结果 |
| 短时断线 | 断开连接后产生少量操作并恢复 | 客户端通过增量追赶恢复至最新正式状态 |
| 长时断线 | 断开后使增量超出近期窗口 | 客户端通过快照加增量恢复至最新正式状态 |
| 慢客户端 | 限制单客户端消费速度 | 有界队列触发降级或断开，不拖垮同房间其他连接 |
| Gateway 重启 | 协作中终止当前 Gateway | 客户端可重新连接，路由恢复，已确认操作不丢失 |
| Redis 故障 | 编辑及读取过程中停止 Redis | 正文和正式操作不丢失；系统按设计降级或恢复 |
| 缓存旧数据 | 更新数据并延迟失效消费 | 版本校验、主动失效或 TTL 在设计时间内清除旧值 |
| 缓存击穿 | 热点 Key 失效后发起并发读取 | Single-Flight 将同 Key 的并发回源限制为一次或设计上限 |
| Outbox 重复发送 | 重复投递同一事件 | Consumer Inbox 及业务约束保证只产生一次业务效果 |
| Kafka 消费者重启 | 处理中停止并重新启动消费者 | 从已提交 Offset 继续，结果不丢失且不重复生效 |
| 搜索索引丢失 | 删除索引并执行重建 | 核心文档功能继续可用；索引可从权威数据恢复 |
| Agent 超时 | 模拟模型超时或不可用 | 返回规则版结果或失败状态；核心编辑和协作线程不受影响 |
| RAG 权限撤销 | 索引仍含旧 ACL 时撤销用户权限并发起审阅 | Core 最终复核移除候选内容，模型上下文中越权 Chunk 数为 0 |
| RAG 版本隔离 | 同一文档存在草稿、有效版本和废弃版本 | 默认只检索有效版本；任务草稿仅对本任务可见 |
| 混合检索 | 使用类名、Endpoint、同义语义及跨文档问题集查询 | 精确标识符和语义证据均达到批准的 Recall@K 基线 |
| RAG 索引重建 | 删除知识索引并从事件或权威数据重建 | Chunk 数量、版本、内容哈希和 Embedding 版本与基线一致 |
| Agent 无效证据 | 返回不存在的 Block、版本或 Diff 标识 | Evidence Verifier 拒绝该结论进入正式 Issue |
| 重复 Review 任务 | 重放同一审阅任务 | 不重复创建正式 Issue |
| MCP 越权查询 | 使用无权主体查询文档 | 请求被拒绝并产生审计记录 |

## 4. 性能验证

| 编号 | 对比或压力场景 | 主要观测项 |
|---|---|---|
| PV-01 | PostgreSQL 直读、Redis + PostgreSQL、Caffeine + Redis + PostgreSQL | 吞吐量、P50/P95/P99、回源次数、缓存命中率 |
| PV-02 | 热点 Key 过期后的并发读取 | 回源并发数、加载延迟、失败率 |
| PV-03 | 多文档均匀负载与单一热文档负载 | 分片队列长度、操作延迟、热点迁移效果 |
| PV-04 | 正常客户端与慢客户端混合连接 | 发送队列、连接数、内存、断开数量及房间延迟 |
| PV-05 | Kafka 逐条消费与批量消费 | 吞吐量、Lag、处理延迟和数据库写入开销 |
| PV-06 | Agent 并发任务与核心请求混合压力 | Agent 队列、核心请求 P99、线程池和连接池使用率 |
| PV-07 | BM25、向量检索及混合检索对比 | Recall@K、MRR、nDCG、查询延迟和资源开销 |
| PV-08 | 不同 Chunk 策略及 Context Token 预算 | 检索质量、Evidence 利用率、Token 和总任务耗时 |

具体容量和响应目标在需求文档 OQ-011 关闭后补充，不在取得数据前声明固定并发能力。

## 5. 故障与恢复实验

| 编号 | 故障 | 预期系统行为 |
|---|---|---|
| FI-01 | Redis 超时或不可用 | 权威正文不丢失；允许的读取回源；限流和 Presence 等能力按设计降级 |
| FI-02 | Kafka 失效消费者延迟 | 本地缓存可能短暂旧读，但由版本控制及 TTL 兜底；延迟可观测 |
| FI-03 | Kafka 积压或毒消息 | Lag 产生告警；毒消息隔离至 DLQ；正常分区处理不被永久阻塞 |
| FI-04 | Elasticsearch 不可用或索引丢失 | 编辑与发布继续可用；搜索降级；恢复后支持重建 |
| FI-05 | Agent 模型超时或结构化输出失败 | 工作流受超时和修订次数限制；返回规则结果或明确失败 |
| FI-09 | Embedding Provider 不可用 | 入库任务重试或进入 DLQ；旧索引继续服务；不发布半成品索引 |
| FI-10 | Core 权限复核不可用 | Agent 任务 Fail Closed，不向模型发送未经复核的候选内容 |
| FI-06 | Core 实例异常退出 | 已提交事务保留；未确认操作可安全重试；缓存可重新加载 |
| FI-07 | Gateway 实例异常退出 | 客户端重新连接并恢复至最后确认序列后的最新状态 |
| FI-08 | 对象存储不可用 | 文档元数据不被破坏；附件操作明确失败或延迟重试 |

## 6. JVM 与资源实验

| 编号 | 实验 | 主要风险与证据 |
|---|---|---|
| JV-01 | 在 Netty EventLoop 注入阻塞操作 | 验证事件循环阻塞对连接延迟的影响及隔离措施 |
| JV-02 | 对慢客户端使用无界与有界队列对比 | 验证内存增长、背压及断开策略 |
| JV-03 | 构造 ByteBuf 未释放场景 | 使用直接内存指标和泄漏检测定位问题 |
| JV-04 | 高频序列化对象分配 | 通过 JFR 和 GC 日志分析 Young GC 压力 |
| JV-05 | 调整 Caffeine 容量及权重 | 比较 Old Generation、GC 暂停和命中率 |
| JV-06 | Agent 与核心任务共享及隔离线程池对比 | 比较核心请求 P99 和线程池饱和情况 |
| JV-07 | 平台线程与虚拟线程处理阻塞后台任务 | 比较吞吐、线程数量、内存和诊断复杂度 |

## 7. MCP Context Server 专项验证

MCP 第一阶段必须使用官方 MCP Inspector 连接真实 `/mcp` 端点，并保存不含凭证的可复核证据。

| 场景 | 验证方法 | 通过条件 |
|---|---|---|
| 协议初始化 | Inspector 发起 `initialize` | 协议协商成功并返回稳定服务名称、版本和能力 |
| 工具发现 | 调用 `tools/list` | 仅返回本阶段批准的两个真实只读 Tool，Schema 可解析 |
| 工作区上下文 | 调用 `devcollab.workspace.get_context` | 返回调用用户有权访问的真实工作区及仓库同步概况 |
| 代码区间 | 调用 `devcollab.code.read` | 从 Worker Git 文件投影返回真实文本与行范围，不读取 `.data` |
| 越权 | 非成员使用真实 Token 调用 | Core 二次授权拒绝，返回 `PERMISSION_DENIED` 并产生脱敏审计 |
| 非法参数 | 传入路径穿越、单边行号或反向范围 | 返回稳定参数错误，不泄露本地路径或堆栈 |
| 上下文预算 | 请求超过行数或字符预算 | 显式返回截断状态和省略行数，不静默丢失 |
| Core 不可用 | 停止或隔离 Core 后调用 | 返回可重试的 `CORE_UNAVAILABLE`，MCP 进程不伪造结果 |
| 日志脱敏 | 检查成功与失败调用日志 | 不出现 JWT、Authorization、完整代码/文档正文、密钥或仓库凭证 |
| 原功能回归 | 运行 Core、Worker、Gateway、Web 与现有 E2E | Git 同步、文件树、工作区删除/重命名和 Linked Workbench 不回归 |

## 8. Agent RAG 专项评测

Agent 阶段必须独立验证检索和生成，不能只以最终示例“看起来正确”作为通过依据。

| 评测层 | 指标 | 通过要求 |
|---|---|---|
| 入库 | Chunk 完整率、重复率、版本准确率、索引重建一致性 | 不丢失已批准来源；确定性 ID 不重复；版本和内容哈希可核对 |
| 检索 | Recall@K、MRR、nDCG、Exact Identifier Recall | 目标值由首批人工标注集建立，混合检索不得低于批准基线 |
| 权限 | Permission Leakage | 所有测试场景必须为 0；任何泄漏阻断 Agent 发布 |
| 上下文 | Context Utilization、过期 Chunk 比例、Token 使用 | 正式结论能够引用 Context Pack；默认不包含过期版本 |
| 审阅 | Issue Precision/Recall、Evidence Validity、Unsupported Claim Rate | 单 Reviewer 相比规则版存在可测量增益后才进入多 Reviewer |
| 工作流 | Checkpoint 恢复、幂等、结构化输出、有限循环 | 重放不重复建 Issue；中断可恢复；节点及修订不超过配置上限 |
| 回归 | Prompt、模型、Embedding、Chunk 和检索参数版本对比 | 任一配置变更必须运行同一评测集并保留前后结果 |

专项样本至少覆盖正常设计、已知缺陷、跨文档冲突、Git 漂移、过期版本、权限撤销、提示词注入和无问题文档。

## 9. 验证记录要求

每项验证至少记录：版本及提交标识、环境配置、数据规模、并发模型、执行步骤、原始指标、关键日志或 Trace、观察结果、结论和遗留问题。失败实验不得删除，应形成缺陷、ADR 修订或故障复盘。
