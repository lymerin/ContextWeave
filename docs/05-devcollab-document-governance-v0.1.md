## 1. 目的

统一 ContextWeave 文档的存放位置、提交属性、编号、命名、正文结构、引用、索引和维护流程。无论文档是否提交 Git，均执行本规范；“本地、不提交”只改变版本库状态，不降低内容质量要求。

## 2. 单一存放位置

- 项目 Markdown 文档统一存放在 `docs/`。
- 根目录不新增散落的项目 Markdown 文档。
- `00-devcollab-document-index.md` 是文档清单和阅读顺序的权威入口。
- Skill、源码、配置和生成产物不因本规范而移动到 `docs/`。

## 3. 文档分类与编号

### 3.1 团队共享文档：00–89

团队需要共同评审、作为产品或工程基线、影响系统行为或需要持续追溯的文档使用 `00–89`，允许提交 Git。

| 编号段 | 用途 |
|---|---|
| 00 | 文档索引 |
| 01–09 | 产品、架构、验证、设计和治理基线 |
| 10–39 | 接口、数据、协议、安全和专项设计 |
| 40–69 | 测试、压测、部署、运维和故障复盘 |
| 70–89 | 发布、迁移及其他共享工程材料 |

共享文档不得被 `.gitignore` 命中。涉及密码、令牌、个人隐私或生产密钥的内容不得写入文档，不能以“可提交文档需要完整”为由记录秘密。

### 3.2 本地文档：90–99

个人排期、学习笔记、面试材料、用户明确要求不提交的技术选型或临时工作记录使用 `90–99`，必须加入 `.gitignore`。

本地文档仍须：

- 标明用途、状态、版本和依据；
- 与正式需求、架构和验证基线保持一致；
- 不虚构完成状态、性能数据或评审结论；
- 在文档索引的“本地文档”部分登记；
- 不成为正式产品范围和架构决策的唯一依据。

编号已占用时，使用下一个未占用的 9x 编号，不覆盖或复用现有文档编号。

### 3.3 分类决策顺序

1. 用户明确要求提交或不提交时，遵循用户要求。
2. 已在文档索引中确定版本库状态时，遵循索引。
3. 影响团队产品、架构、接口、安全或验收基线时，默认共享。
4. 仅服务个人执行、学习或面试时，默认本地。
5. 无法可靠判断时，先停止创建并确认，不能仅凭文件名猜测。

## 4. 文件命名

### 4.1 共享文档

```text
NN-devcollab-<topic>-v<major>.<minor>.md
```

示例：

```text
04-devcollab-frontend-design-v0.2.md
05-devcollab-document-governance-v0.1.md
```

### 4.2 本地文档

```text
9N-local-<topic>-v<major>.<minor>.md
```

示例：

```text
90-local-development-plan-v0.2.md
92-local-frontend-technology-adr-v0.1.md
```

命名要求：

- 使用两位数字编号、小写英文主题和连字符。
- 文件名表达主题，不写“最终版”“最新版”“new”等临时词。
- 正文标题使用清晰中文名称，不机械复制文件名。
- 同一文档升级版本时保留主题名称，按版本策略处理旧版。

## 5. 正文结构

### 5.1 必需内容

除文档索引等特殊清单外，文档至少包含：

1. 一级标题；
2. `文档信息`；
3. 目的或背景；
4. 正文主体；
5. 明确的结论、验收条件或待确认事项；
6. 与相关基线文档的引用。

`文档信息`至少记录文档类型、状态、版本、日期和适用范围或依据。不得把未评审草案标记为“生效”或“已接受”。

### 5.2 内容要求

- 先写结论和边界，再写实现细节。
- 需求、架构、验证、设计和个人计划分开表达。
- 每个必须执行的要求应可测试、可评审或可追溯。
- 不重复粘贴其他文档的大段内容；使用相对链接或文件名引用。
- 不用无依据的“企业级、高并发、高可用”等表述。
- 性能和容量数据必须注明测试条件；未测试时写“待验证”。
- 待确认项与已决定事项分开，不能把建议写成既定事实。
- 技术缩写首次出现时说明含义，后续保持术语一致。

### 5.3 图表与示例

- 静态结构、状态和流程优先使用 Mermaid。
- 页面布局可使用标注清晰的低保真文本图或受版本管理的图片资产。
- 图表必须服务于关系、顺序或布局说明，不为装饰而添加。
- 示例数据必须标明是示例，不能被误认为真实业务或压测结果。

## 6. 引用和链接

- `docs/` 内文档互相引用时优先使用相对文件名。
- 引用外部技术事实时优先使用官方文档、标准或源代码仓库。
- 外部资料可能变化时记录访问日期或在评审时重新确认。
- 重命名文档时必须搜索并更新所有入站引用、索引和 `.gitignore`。
- 不在正式文档中引用仅存在于个人机器的绝对路径。

## 7. 文档状态与版本

建议状态：

```text
草案 → 待评审 → 生效 → 已替代 / 已废弃
```

- 小范围勘误、不改变要求或结论：增加 minor 版本。
- 改变范围、关键决策、接口或验收：增加 major 版本或按项目评审规则创建新版本。
- 新版本替代旧版本时，旧文档须明确指向替代版本。
- 文件名、正文版本和索引版本必须一致。
- 本地文档同样使用版本号，但不因未提交 Git 而省略状态管理。

## 8. 索引和 Git 规则

创建、重命名、改变提交属性或删除文档时，必须同步更新：

1. `docs/00-devcollab-document-index.md`；
2. `.gitignore`；
3. 其他文档中的引用；
4. 文档正文的状态和版本信息。

共享文档在索引中标为“应提交”，且不能匹配 `.gitignore`。本地文档在索引中标为“已由 `.gitignore` 忽略”，并使用精确文件路径规则，不用 `docs/9*.md` 这类过宽模式。

`.gitignore` 不能移除已经被 Git 跟踪的文件。若文档曾被跟踪，需在有效仓库中另行执行取消跟踪操作；操作前先确认不会删除工作区文件。

## 9. 安全和真实性

- 禁止记录密码、Access Token、Refresh Token、Git Token、私钥、Cookie、生产连接串和未脱敏个人数据。
- 日志、错误和截图中的敏感信息必须脱敏。
- 不提交和不记录是两件事：本地文档也不能保存秘密。
- 不伪造覆盖率、性能结果、完成百分比、用户调研或评审签字。
- 结论来自现有代码、测试或资料时，明确证据边界；缺少证据时标为待验证。

## 10. 文档操作流程

### 10.1 新建

1. 读取本规范和文档索引。
2. 确认提交属性。
3. 选择未占用编号和规范文件名。
4. 基于真实需求或证据编写。
5. 更新索引、引用和 `.gitignore`。
6. 检查标题、元数据、版本、代码围栏和链接。

### 10.2 更新

1. 保留原文档意图和已确认边界。
2. 判断是否需要升级版本。
3. 更新受影响的索引、引用和关联文档。
4. 不顺手修改无关文档内容。

### 10.3 重命名或移动

1. 确认源文件、目标路径和编号均在 `docs/`。
2. 确认目标不存在，避免覆盖。
3. 移动后搜索旧文件名的所有引用。
4. 更新索引和 `.gitignore`。
5. 在有效 Git 仓库中检查跟踪与忽略状态。

## 11. 完成检查清单

- [ ] 文档位于 `docs/`。
- [ ] 编号与提交属性一致且未重复。
- [ ] 文件名、正文版本、索引版本一致。
- [ ] 文档信息完整，状态真实。
- [ ] 内容来自明确需求、代码或资料，没有无依据结论。
- [ ] 共享文档未被忽略；本地文档已精确忽略。
- [ ] 索引和全部文件引用已更新。
- [ ] Markdown 代码围栏成对，Mermaid 结构完整。
- [ ] 不包含秘密、敏感日志或未脱敏数据。
- [ ] 改动范围仅覆盖本次文档任务。
