## 2. 项目定义

### 2.1 产品定位

ContextWeave 是面向 2～10 人软件开发团队的实时工程知识协作平台。系统以版本化工程文档为核心，连接文档、代码变更、工程评审和编程 Agent 上下文，帮助团队确认当前有效设计，并及时发现代码与文档不一致及工程方案缺项。

ContextWeave 通过标准 Model Context Protocol（MCP）能力向编程 Agent 和外部 AI 客户端提供受权限控制的代码、文档与关联上下文。MCP 是可信工程能力入口，不是聊天机器人页面，也不是另一套 Git 文件系统。

### 2.2 需要解决的问题

1. 需求、架构、接口、数据库和测试材料分散，团队无法确认当前有效版本。
2. 代码或接口变化后，关联文档未同步更新。
3. Pull Request 合并后，测试、压测、异常处理等工程事项仍可能缺失。
4. 小型团队缺少持续的架构与可靠性审阅能力。
5. 编程 Agent 可能读取草稿、过期方案或无权限内容，产生错误修改建议。
6. 项目结束后无法追溯设计变更、决策依据和未关闭风险。

### 2.3 产品目标

- 建立唯一、可追溯的工程文档版本基线。
- 支持小型团队安全地共同编辑、评审和发布工程文档。
- 将代码路径及变更与对应工程文档建立关联。
- 通过确定性规则和 Agent 审阅发现有证据支撑的工程风险。
- 向编程 Agent 提供经过权限过滤、版本确认的可信上下文。
- 形成可部署、可测试、可压测和可故障恢复的完整交付物。

### 2.4 成功判定

完整产品闭环应完成以下业务流程；其中核心协作、Git、搜索和 MCP 属于 V1.0，内部 Agent 工程审阅属于后续 V1.1：

```text
团队创建工作空间
→ 创建并协作编辑工程文档
→ 提交评审并发布有效版本
→ 关联代码仓库及代码路径
→ 代码变化触发漂移检查和工程审阅
→ 负责人处理审阅问题
→ 编程 Agent 查询到当前有效且有权限的工程上下文
```

上述闭环必须通过真实演示、自动化测试或故障实验验证，不以仅完成页面、接口或架构代码作为验收依据。

## 3. 用户与权限

### 3.1 目标用户

- 软件工程课程及竞赛团队；
- 实验室小型软件项目；
- 学生创业团队；
- 小型开源项目维护团队；
- 有自托管工程知识需求的小型开发团队。

### 3.2 工作空间角色

| 角色 | 权限范围 |
|---|---|
| ADMIN | 管理工作空间、成员、文档、模板、规则和评审流程 |
| MEMBER | 创建和编辑文档、评论、提交评审及处理被授权事项 |

无权用户不是工作空间角色。已登录用户如果不存在于目标工作空间的成员关系中，则不得访问该工作空间、文档、Block、成员列表、WebSocket 房间或 MCP 上下文。

### 3.3 文档权限

系统应支持 `READ`、`COMMENT`、`EDIT`、`REVIEW`、`MANAGE` 五类文档权限。最终权限由工作空间角色、文档级授权、分享授权和文档状态共同计算。

业务规则：

- 未授权用户不得通过页面、接口、WebSocket 或 MCP 获取文档内容。
- 文档发布、废弃、权限调整等高风险操作必须记录操作者、时间、对象及结果。
- 成员被禁用或移除后，其后续请求和实时连接不得继续获得原工作空间权限。
- 已发布版本只读，任何修改必须形成新草稿。

## 4. 产品范围与优先级

优先级定义：

- P0：首期 MVP 必须具备，缺失时无法形成基本业务闭环。
- P1：V1.0 核心差异化能力。
- P2：后置增强能力，只在 P0、P1 及其数据基础稳定后实施。

| 模块 | 优先级 | 版本范围 |
|---|---:|---|
| 账号、工作空间、成员与权限 | P0 | MVP |
| 工程文档树与块式编辑 | P0 | MVP |
| 评论、评审、版本发布与历史 | P0 | MVP |
| Block 级实时协作、冲突和断线恢复 | P0 | MVP |
| 审计与基础安全 | P0 | MVP |
| 代码仓库关联与文档漂移 | P1 | V1.0 |
| Agent 工程审阅、RAG 及证据校验 | P2 | V1.1 |
| 工程完成度验证 | P1 | V1.0 |
| 搜索与附件 | P1 | V1.0 |
| MCP 可信上下文 | P1 | V1.0 |
| 分享链接、导出和高级通知 | P2 | 增强版本 |

### 4.1 明确不做

- 通用个人笔记、内容社区或企业 OA；
- 完整项目管理、工时、财务和商业计费；
- Google Docs 级字符级协同编辑；
- 自动执行任意用户仓库代码；
- Agent 自动合并代码或直接修改已发布文档；
- 多地域强一致协作；
- 自研数据库、搜索引擎、消息队列、对象存储或大模型。

## 5. 核心业务对象与规则

### 5.1 工程文档类型

首期应预置以下类型：需求说明、架构设计、技术决策记录、接口契约、数据库设计、测试计划、压测报告、故障复盘、发布说明。

各类型可使用不同模板或结构规则，但必须共用统一的版本、权限、评论和评审机制。

### 5.2 文档状态

```text
DRAFT → IN_REVIEW → PUBLISHED → SUPERSEDED / DEPRECATED
```

业务规则：

1. 新建文档默认为 `DRAFT`。
2. 只有具备评审权限的用户可处理评审结论。
3. 评审通过后方可发布；发布生成不可变版本。
4. 新版本发布后，原有效版本转为 `SUPERSEDED`。
5. 不再适用且没有替代版本的文档可标记为 `DEPRECATED`。
6. 评论、审阅问题、代码关联和 Agent 证据必须指向明确文档版本或 Block。

### 5.3 审阅问题状态

```text
OPEN → ACCEPTED / REJECTED / RESOLVED
```

- `OPEN`：问题待处理。
- `ACCEPTED`：团队承认风险，但决定暂不解决，必须记录原因。
- `REJECTED`：判定为误报或不适用，必须记录原因。
- `RESOLVED`：问题已修复，并应可关联修复后的文档版本或代码变更。

## 6. 功能需求

### 6.1 账号、团队与访问控制

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---:|---|
| FR-AUTH-001 | 用户可以注册、登录、刷新会话和退出 | P0 | 正常流程可用；失效凭证被拒绝；退出后刷新凭证不可继续使用 |
| FR-AUTH-002 | 用户可以创建工作空间并管理基本信息 | P0 | 创建者自动成为 ADMIN；不同工作空间数据隔离 |
| FR-AUTH-003 | ADMIN 可以邀请、禁用、移除成员并调整允许的角色 | P0 | 权限立即按安全规则生效；操作留有审计记录；不得移除或降级最后一名 ADMIN |
| FR-AUTH-004 | 系统按角色、文档授权和文档状态执行权限校验 | P0 | REST、WebSocket、内部接口和 MCP 的结果一致 |
| FR-AUTH-005 | 系统限制登录、Agent 和高风险操作频率 | P0 | 超限返回明确结果，不影响其他用户正常请求 |
| FR-AUTH-006 | 用户可创建有有效期的只读或评论分享链接 | P2 | 过期、撤销或越权链接不可访问 |

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---:|---|
| FR-DOC-001 | 用户可以在工作空间内创建多级文档树 | P0 | 支持创建、重命名、移动、归档；无管理权限不可删除 |
| FR-DOC-002 | 文档由可独立操作的 Block 组成 | P0 | 至少支持标题、段落、代码、引用、待办、表格和图表 Block |

| FR-DOC-004 | 用户创建文档时可以选择工程文档类型和模板 | P0 | 类型被保存并可用于筛选、校验和审阅 |
| FR-DOC-005 | 用户可以查看版本历史及版本差异 | P0 | 版本内容、创建人、时间和状态可追溯 |

| FR-DOC-007 | 用户可以上传并引用图片和附件 | P1 | 文件与工作空间、文档及上传者关联；删除状态可追踪 |
| FR-DOC-008 | 用户可以导出指定版本 | P2 | 导出内容与选择的不可变版本一致 |

### 6.3 实时协作

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---:|---|
| FR-COLLAB-001 | 多名成员可进入同一文档房间并看到在线状态 | P0 | 加入、离开和失活状态能够更新 |
| FR-COLLAB-002 | 不同 Block 的修改可并行提交并同步给其他成员 | P0 | 两个浏览器可观察到相同的已确认结果 |
| FR-COLLAB-003 | 同一 Block 并发修改时系统必须检测版本冲突 | P0 | 返回冲突，不允许后写内容静默覆盖先写内容 |
| FR-COLLAB-004 | 客户端重试同一操作不得造成重复修改 | P0 | 重复操作返回原结果或等价成功结果 |
| FR-COLLAB-005 | 客户端应收到操作已确认、冲突或失败的明确结果 | P0 | 未持久化成功的操作不得作为正式结果广播 |
| FR-COLLAB-006 | 用户短时断线后可增量追赶操作 | P0 | 恢复后内容与服务端一致，不重复应用操作 |
| FR-COLLAB-007 | 用户长时间断线后可通过快照和后续操作恢复 | P0 | 恢复结果与最新正式文档状态一致 |
| FR-COLLAB-008 | 慢客户端不得拖垮同房间其他连接 | P0 | 触发降级或断开时有明确原因，服务资源有边界 |

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---:|---|
| FR-REV-001 | 用户可对文档或指定 Block 发表评论 | P0 | 评论保留作者、时间、对象和处理状态 |
| FR-REV-002 | 编辑者可将草稿提交评审并指定评审人 | P0 | 状态变为 `IN_REVIEW`；未授权用户不能审批 |
| FR-REV-003 | 评审人可提出、接受、拒绝或解决审阅问题 | P0 | 每次状态变化记录操作者、时间和说明 |
| FR-REV-004 | 评审通过后可发布不可变版本 | P0 | 当前有效版本唯一；旧版本仍可查询 |
| FR-REV-005 | 用户可废弃当前文档或用新版本替代 | P0 | 查询结果明确显示有效、被替代或废弃状态 |

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---:|---|

| FR-GIT-002 | 用户可将文档或 Block 与一个或多个代码路径关联 | P1 | 关联关系可创建、查看、修改和解除 |

| 编号 | 需求 | 优先级 | 验收要点 |

| FR-AGENT-010 | 检索内容进入模型前必须完成版本过滤和 Core 最终权限复核 | P2 | 已撤权、过期或超出任务范围的内容不会进入 Context Pack；权限泄漏为 0 |
| FR-AGENT-011 | 审阅工作流采用有状态、可恢复且步骤受限的编排 | P2 | 节点、Tool、并行数、重试、修订、Token 和时间具有硬上限；中断可从 Checkpoint 恢复 |
| FR-AGENT-012 | 系统维护检索及审阅评测集并执行回归评测 | P2 | 可报告 Recall@K、版本准确率、权限泄漏、Issue Precision/Recall 和 Evidence 有效率 |

### 6.9 MCP 可信上下文

| 编号 | 需求 | 优先级 | 验收要点 |
|---|---|---:|---|
| FR-MCP-001 | 编程 Agent 可搜索已批准的工程文档 | P1 | 只返回调用用户有权访问的内容 |
| FR-MCP-002 | 编程 Agent 可查询当前有效 API、数据库设计和 ADR | P1 | 返回版本、状态、发布时间和废弃标识 |
| FR-MCP-003 | 编程 Agent 可按代码路径查找关联文档 | P1 | 结果包含当前有效版本、漂移状态和未解决问题 |
| FR-MCP-004 | 编程 Agent 可比较版本并查询开放问题 | P1 | 返回稳定引用，不直接访问底层数据库 |
| FR-MCP-005 | 每次 MCP 调用均执行认证、授权、限流和审计 | P1 | 越权请求被拒绝并记录；工具为只读操作 |

第一阶段 MCP 仅开放只读能力，不允许通过 Tool 修改代码、文档或关系。后续 Agent 只能提交结构化的待审核变更方案，由用户审核后通过 Core 事务应用；Agent 不得直接覆盖正式文档。MCP 读取 Worker 已生成的 Git 投影，不直接访问克隆目录或建立第二套仓库文件系统。

## 7. 非功能需求

### 7.1 数据一致性与可靠性

- PostgreSQL 中的业务及文档状态为权威数据；缓存、搜索索引和对象处理结果不得反向覆盖权威状态。
- 正式协作操作必须持久化成功后才能确认并广播。
- 业务状态修改与待发送事件必须保证不永久丢失；重复事件不得造成重复业务效果。
- Redis、搜索服务或模型服务不可用时，核心文档读取、编辑和发布链路应按设计降级。
- 已发布版本、审阅证据和审计记录必须具备稳定引用。

### 7.2 安全

- 密码必须使用成熟密码哈希方案保存，令牌及仓库凭证不得明文记录到日志。
- 所有外部入口均执行身份验证和工作空间数据隔离。
- Markdown、HTML、附件和分享内容必须进行安全校验，防止 XSS 和危险文件访问。
- Agent 不得拥有任意数据库写入、系统命令执行或自动修改已发布内容的能力。
- 文档中的提示内容不得覆盖 Agent 的系统安全约束。

### 7.3 性能与容量

- 基准使用场景为单工作空间 2～10 名成员协作。
- 所有连接队列、缓存、任务队列、附件和 Agent 调用均必须设置容量或用量边界。
- 首个可运行版本完成后，应通过压测确定 HTTP、实时操作、恢复和搜索的基线数据；Agent 审阅的性能与成本基线在 V1.1 单独评测。在测试前不声明企业级并发或固定可用性等级。
- V1.0 发布评审前必须确定目标数据量、并发量及关键操作响应目标，相关数值见第 10 节待确认项。

### 7.4 可观测性与可运维性

- 关键链路能够通过 Trace ID、Document ID、Operation ID、Event ID 和 Workflow ID 关联查询。
- 系统应提供实时连接、操作延迟、冲突、缓存、异步积压、Agent 成功率及运行时资源指标。
- 核心异常应记录结构化日志，但不得记录密码、令牌、仓库凭证和完整敏感文档内容。
- 系统应支持容器化启动，并提供环境配置、初始化、健康检查、备份和恢复说明。

### 7.5 测试要求

- P0 功能必须具备单元测试和关键链路集成测试。
- 数据库、缓存、消息等集成行为不得只用 Mock 证明。
- 实时协作、权限、幂等、版本发布和恢复必须具备端到端测试。
- 每项核心中间件至少完成一个故障与恢复实验，并保留结果。

## 8. MVP 验收范围

MVP 通过需同时满足以下条件：

1. 用户可注册登录、创建工作空间、邀请成员并按角色隔离权限。
2. 用户可创建工程文档，编辑多个 Block，并在文档树中移动或归档。
3. 两个浏览器可在同一文档中编辑不同 Block，并看到服务端确认后的相同结果。
4. 同一 Block 并发修改产生明确冲突，重复提交不会重复修改。
5. 用户断线后可恢复到最新正式内容，缓存或实时连接组件重启不造成正文丢失。
6. 草稿可提交评审并发布为不可变版本；新版本不得覆盖历史版本。
7. 无权限用户通过页面、接口和实时连接访问均被拒绝。
8. 关键操作具备审计记录，核心链路可在本地容器环境完整运行。

不满足以上任一项时，不应以“后端接口已完成”或“页面已展示”判定 MVP 完成。

## 9. V1.0 验收范围

在 MVP 通过基础上，V1.0 还需满足：

1. 可绑定至少一种已确认的 Git 平台，并同步真实 Commit、PR 和文件差异。
2. 代码路径变化能够生成带真实文档与代码证据的漂移问题。
3. 搜索、附件、通知和工程完成度验证形成可用闭环。
4. MCP 按用户权限返回当前有效文档、关联代码及开放风险，越权访问被拒绝并审计。
5. 搜索、缓存、Redis 或消息组件出现设计内故障时，系统行为符合降级或恢复要求。
6. 交付压测报告、故障实验、部署说明、关键 ADR 和端到端演示。

## 10. V1.1 Agent 验收范围

Agent 阶段只有在 V1.0 核心平台稳定后启动，并应满足：

1. 文档发布和 Git 变更可以幂等生成带版本元数据的知识 Chunk，索引可全量重建。
2. 混合检索同时覆盖精确工程标识符和语义相关内容，检索质量达到评审批准的基线。
3. 任何 Chunk 进入模型前均通过 Core 权限复核；权限隔离测试的内容泄漏数为 0。
4. LangGraph 工作流可从 Checkpoint 恢复，模型 Tool、并行数、重试、修订及成本具有硬上限。
5. 单 Reviewer 相比规则版产生可测量增益后，才允许启用多个专业 Reviewer。
6. Agent 对锁定版本执行审阅，模型或检索失败时可降级，且不影响核心协作链路。
7. 无有效 Evidence 的候选结论不会进入正式问题列表。
8. Prompt、模型、Embedding、Chunk 策略和检索参数变更均执行回归评测。

## 12. 需求变更规则

- 本文经评审后作为产品范围基线，新增 P0/P1 功能必须记录变更原因、影响版本和验收调整。
