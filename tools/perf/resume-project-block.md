## 一、Agent 岗版本

**ContextWeave｜持续演化代码库的工程知识基础设施｜核心开发**

将源码编译为可验证、可追溯的语义知识快照，使 Agent 在版本、权限和证据边界内生成工程文档，并随代码演进持续修复知识失真。

**技术栈：** Python、FastAPI、DeepSeek、MCP、Java 21、Spring Boot、PostgreSQL、Redis、gRPC

- **大仓库语义规划：** 为解决全仓元数据超出模型预算、按文件切分割裂业务边界的问题，构建包含模块、依赖与 Binding 的 ProjectIndex，按顶层模块确定性分片并行规划，再合并为全仓方案；程序拒绝未知文件、重复 Unit 和越界文档，使模型只决定语义分组，任务边界始终受控。

- **可信上下文编译：** 为避免同名符号碰撞和错误依赖污染 Agent 判断，将源码编译为 Symbol Atom、调用图与正反向索引；跨文件引用仅按 import 和 alias 作用域解析，候选缺失或多于一个一律标记 `UNRESOLVED`，再按结构距离裁剪上下文，生成绑定 Revision 的稳定 ContextSnapshot。

- **受控文档生成：** 为解决模型随意组织结构、遗漏符号和伪造内部 ID 的问题，由程序零模型调用生成文档骨架、槽位和批次，模型只撰写正文；通过权威快照完成 `symbol_key` 到 `atom_id` 的绑定，并以 Coverage、Evidence、Revision Gate 校验结果，缺失内容最多定向修复两次，失败内容不进入写入链路。

- **可恢复执行引擎：** 为保证分钟级批量任务在 Worker 崩溃和并发执行下不丢进度、不重复修改文档，将 Job 与 Unit 持久化，通过 `FOR UPDATE SKIP LOCKED`、Lease、Heartbeat 实现并发领取和故障接管；按目标文档排他调度，评审等待不消耗重试预算，并区分模型失败与基础设施瞬时故障。

- **最小权限 MCP：** 为防止 Agent 越权读取仓库、调用未授权工具或使用过期代码，设计绑定用户、Job、Workspace、Repository、Revision 与 `allowed_tools` 的短期委托令牌；MCP 执行前校验工具及资源作用域，递归检查嵌套参数，Revision 变化立即拒绝，并记录调用耗时、数据量与错误码。

- **MCP 热路径优化：** 针对单次任务产生 370 次会话初始化和 762 次 Token 交换的问题，将 Session 调整为 Unit 内复用、Token 调整为 Unit 内 TTL 复用，并将代码、文档结构和候选查询收敛为批量工具；所有优化均支持独立开关与快速回退，固定仓库、Commit 和 Scope 的 A/B 实测中，会话初始化下降 89%，Token 交换下降 85%，工具调用下降 23%，整体调用 p95 下降 16%。

- **跨语言契约治理：** 为避免 Java 与 Python 工具字段独立演进造成运行期协议错误，将 25 份 MCP 输入输出 Schema 收敛为仓库级单一契约源，Java 端直接加载、Python 端运行时校验并执行契约测试，将字段缺失和批量工具兼容问题前移至测试与联调阶段。

## 二、Java 后端岗版本

**ContextWeave｜持续演化代码库的工程知识基础设施｜核心开发**

围绕代码、工程文档与 Agent 变更建立统一知识治理平台，使机器生成内容与人工编辑共享一致的版本控制、权限校验和变更审查语义。

**技术栈：** Java 21、Spring Boot、PostgreSQL、Redis、Kafka、gRPC、Python、FastAPI、MCP

- **符号级知识自愈：** 为解决代码移动、改名和签名变化导致文档锚点长期失真的问题，以 `symbol_key`、签名和目标 Block 建立代码文档 Binding；新 Revision 按精确符号、限定名和同文件范围逐级重定位，区分行号位移、签名变化、符号移动、符号删除与文件删除五级漂移并分级处置（位移仅更新锚点、签名变化同步替换正文签名、移动迁移路径、删除移除绑定）。确定性修复自动应用无需人工审批，但证据不足时不猜不删，解析器语言不兼容时跳过检测，避免自动化误伤知识资产。

- **Agent 变更事务：** 为防止 Agent 基于旧上下文覆盖用户修改，将生成结果转换为有序 Operation、Binding Proposal 与 Evidence；通过 `clientRequestId` 和内容指纹识别安全重放与幂等冲突，应用前重新校验文档状态、Block Version 和 Binding 快照，任一目标变化即整单拒绝，文档、绑定和评审状态在同一事务内提交。

- **实时协作一致性：** 为解决网络重试、并发编辑和断线重连造成的重复写入与状态缺口，Gateway 通过 Redis Lua 原子去重，Core 使用操作 ID 与内容指纹保证最终幂等；同一文档通过行锁分配单调递增序列，Block 使用 `expectedVersion` 检测冲突，客户端按序列游标补齐断线期间操作。

- **内部 RPC 重构：** 为降低 Gateway 与 Core 高频权限校验、协作写入和断线补偿的协议开销，抽取独立 Protobuf Contract Module，并通过配置保留 HTTP 回退链路；统一管理长连接 Channel、Deadline、JWT Metadata 和消息上限。同服务同语义各 600 样本中，权限校验 p95 下降 27.4%，断线补偿下降 24.6%，协作写入下降 19.3%。

- **跨服务委托权限：** 为避免 Agent Service 获得不受限制的系统身份，由 Knowledge Core 签发绑定用户、任务、仓库、版本和工具集合的短期令牌；MCP 在调用边界重新校验资源作用域，用户身份沿 Agent、MCP、Core 全链路传递，使机器操作始终受原用户权限和任务范围约束。

- **多语言契约治理：** 为解决 Java MCP Server 与 Python Agent 字段漂移难以及时发现的问题，将 25 份 MCP Schema 统一为仓库级权威契约，Java 端直接加载、Python 端运行时验证并执行契约测试，将协议错误从线上调用阶段前移到构建与联调阶段。

## 三、Block 结构说明（每条负责证明什么）

### Agent 岗（主线为 Agent，Java 侧仅作支撑）
1. 大仓库语义规划 → 复杂任务如何拆对、边界如何受控
2. 可信上下文编译 → Agent 上下文为什么可信（不是 RAG 拼接）
3. 受控文档生成 → 如何避免模型漏内容、伪造 ID
4. 可恢复执行引擎 → 长任务如何并发、恢复、不重复
5. 最小权限 MCP → 防止 Agent 越权上下文（不是普通 RBAC）
6. MCP 热路径优化 → 性能设计做了什么、效果如何
7. 跨语言契约治理 → 协议如何不漂移（支撑点，可后置）

### Java 岗（主线为 Java，Agent 仅作业务入口）
1. 符号级知识自愈 → 代码演进后文档为什么不失真
2. Agent 变更事务 → Agent 如何安全修改正式知识（比 Outbox 更贴业务）
3. 实时协作一致性 → 重放、一致、恢复语义（不是"做了 WebSocket"）
4. 内部 RPC 重构 → 协议重构如何灰度与验证
5. 跨服务委托权限 → 身份沿链传递与作用域校验
6. 多语言契约治理 → 工程治理亮点（版面足够再放）

### 明确淘汰（不作为主 Block）
- PostgreSQL 唯一事实源、Outbox/Inbox/DLQ 架构清单、Caffeine 与 Redis 比较、普通 RBAC、CRUD 模块划分
- 未实现的跨 Job 增量缓存、有混杂因素的总耗时下降（-72%）、只罗列状态机/表名/接口/字段

## 四、面试附录（不上简历）

### 1. 60 秒口头叙事线

> 这个项目解决一个真实问题：**工程文档总是过期**——代码改了，文档没人维护，接口说明逐渐变成谎话。
> 我们做了一套面向持续演化代码库的知识基础设施：把源码编译成可验证、可追溯的语义知识快照，
> Agent 在固定代码版本、最小权限和证据约束下生成文档；代码演进后自动发现并修复知识失真。
> 三条主线：第一，**可信上下文**——跨文件引用只按作用域解析，候选缺失或不唯一就标 UNRESOLVED，
> 宁可少召回也不建错误关系；第二，**受控写入**——结构、ID、引用全部由程序生成，模型只写正文，
> 产出必须走 Review 和 Change Request，Agent 是普通客户端；第三，**可恢复执行**——长任务崩溃
> 从断点恢复、不重复写入，性能上把 370 次 MCP 初始化压到 42 次、762 次 Token 交换压到 114 次，
> 同仓库同 commit 的 A/B 实测、默认关闭可独立回滚。面试官问任何一个数字，背后都有实验记录。

### 2. 防考问题（重点条目）

**A6（MCP 热路径优化）—— 可完整背书，背熟：**
1. 370 次怎么统计的？→ agent 侧 perf 指标按 job_id 过滤，会话初始化由池层计数器记录。
2. 为什么降到 42 而不是 1？→ 41 个单元各自有 delegation 生命周期 + 1 次 discovery；优化消除的是 Unit 内重复初始化，不是跨 Unit 复用。
3. TTL 为什么 300s？→ 模型调用 p50 ≈ 41s，单 Unit 执行周期 < 300s，覆盖 Unit 内所有工具调用；同时小于 delegation 本身 TTL，留安全边界。
4. token 缓存会不会削弱安全？→ 令牌仍由 Knowledge Core 签发（HMAC256 + issuer/audience），缓存只省交换往返、不省校验；Key Lock 防并发击穿。
5. 批量工具怎么过权限模型？→ allowed_tools 同步补齐批量工具名；MCP 服务端按 workspace/repository/工具名校验作用域（对应契约治理修复的授权遗漏缺陷）。
6. 为什么 P95 只降 16%？→ 链路大头是模型调用（p50 41s），MCP 层延迟占比本就小；优化价值在次数与往返（-89%/-85%/-23%），P95 是附带收益——主动说，是加分项。
7. list_files 为什么从 1 涨到 42？→ on 轮执行路径每单元一次 list_files（42 次），换来 66+123+61 次单文件调用收敛为批量调用，总调用仍 -23%。⚠️ 这条请按 on/off 轮 by_tool 数据再核对一遍归因，别点名"分阶段流水线"。

**J4（内部 RPC 重构）** —— 已核实
- 600 样本怎么来的？→ CoreTransportBenchmarkIT 默认 `iterations=200 × rounds=3` = 每链路每协议 600 次采样；同 fixture、同一真实服务、HTTP 与 gRPC 客户端并行对拍。
- 三条链路各测什么？→ access = 文档访问权限校验（Verifier）、catch-up = 断线补偿（先 apply 同一 fixture 再读取追平）、apply = 协作写入（UPDATE_TEXT）；均为真实调用链。
- 具体数字：权限校验 p95 4.920→3.571ms、断线补偿 7.861→5.924ms、协作写入 20.631→16.659ms。
- HTTP 保留回退，灰度怎么切？→ 配置切换 + 保留旧链路；本地数据只决定是否进入预发布验证，不直接授权删除 HTTP Client。
- ⚠️ 跑 benchmark 时若改过 iterations/rounds 参数，"600"需按实际重算。

**J1（符号级知识自愈）** —— 已核实
- 漂移分几级、各自怎么处置？→ 五级：行号位移（仅更新锚点）/ 签名变化（更新绑定 + 替换 Block 正文签名）/ 符号移动（迁移路径）/ 符号删除与文件删除（移除绑定）。
- 修复需要人工审批吗？→ 不需要——确定性修复全部自动应用（drift change request 创建后立即 apply，"静默管线"）；人工审批只用于 Agent 生成的文档变更，两者不要混谈。
- 为什么"证据不足不修"？→ 两个安全阀：语言前缀整体不兼容时跳过整仓检测；单个 binding 在符号表无匹配语言前缀时拒绝判定 SYMBOL_REMOVED——无法证明删除时不删，防止误伤。

**J2（Agent 变更事务）**
- 幂等键冲突怎么识别？→ clientRequestId 相同但内容指纹不同 = 复用冲突，拒绝；相同 = 安全重放，返回原结果。
- 为什么整单拒绝而不是部分应用？→ 基于旧上下文的覆盖会丢用户修改，拒绝整条请求保持一致性。

**J3（实时协作一致性）**
- Redis Lua 挂了对齐怎么办？→ 退化本地去重；最终幂等由 Core 的 clientOperationId + 指纹兜底。
- documentSequence 为什么必须单调？→ 断线恢复的分页锚点，乱序会导致漏操作。

**A2/A3（可信上下文编译 / 受控文档生成）**
- 候选为 0 或 >1 都标 UNRESOLVED，会不会误伤？→ 宁可少召回不建错误关系；误伤只是缺一条候选，错误关系会污染整个知识图。
- Coverage Gate 以什么为基准？→ 目标符号清单（骨架计划产出）；Repair 最多两次，耗尽失败不落库。

### 3. 红线（诚实边界）

- ❌ 不写：总耗时 -72%、重试 -90%、退避 -90%（混杂审批提速）；"Job 级会话复用""跨 Job Token 缓存""blobSha 跨版本增量"（实现为 Unit 级）。
- ❌ 不写「完成后以 Tool 调用数、传输字节、增量解析命中率…进行 A/B 验证」——那是计划不是结果。
- ⚠️ 剩余待核实：跑 core-transport benchmark 时的实际参数（默认 200×3=600，若改过需重算）；25 份 schema 如再变需更新数字。J1 五级漂移、自动应用与 J4 链路语义均已按代码核实。
- ✅ 可放心展开：初始化 -89%、Token 交换 -85%、调用 -23%、p95 -16%（同仓库/commit/scope/指令，仅切开关；两轮各 3 个失败单元，规模可比）；4 个缺陷修复。
